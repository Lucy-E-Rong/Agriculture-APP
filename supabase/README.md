# Supabase Setup

Apply migrations in `supabase/migrations` to a Supabase Postgres project.

The current repository contains local schema/configuration only. Applying a
migration, creating environment variables, or changing a Supabase project is a
separate authorized deployment step.

## Storage

Migration `002_scan_persistence.sql` creates/configures this private bucket:

```text
scan-images
```

Object path for the compressed JPEG actually submitted to the model:

```text
demo/YYYY/MM/DD/{scan_id}.jpg
```

Use UTC for `created_at`. The path date is organizational only; the Postgres
table is not partitioned by day.

The FastAPI backend uploads, signs reads, and deletes images with the Supabase
service role key. Mobile/web clients must never receive that key. No
`anon`/`authenticated` Storage policies are created for the current shared-code
Demo, so app clients cannot access objects directly. The bucket accepts JPEG
objects up to 5 MB and remains private.

## Successful scan write contract

Only a complete successful scan is eligible for Recent Scans:

1. Validate the provider's complete `AnalyzeScanResponse`.
2. Generate a UUID scan ID and a UTC completion timestamp.
3. Upload the compressed JPEG to `demo/YYYY/MM/DD/{scan_id}.jpg`.
4. Insert one `scans` row using the same ID and object path.
5. Return success only after both the object and row exist.

Required persistence values:

- `status = 'succeeded'`
- `data_stage = 'demo'`
- `data_purpose = 'user_upload'`
- `image_mime_type = 'image/jpeg'`
- `analysis_result` is the complete validated response JSON
- summary columns (`stress_level`, `severity_score`, `confidence`,
  `diagnosis`, `detected_issues`, `recommendations`, and
  `needs_human_review`) match `analysis_result`

`location_snapshot` holds display text/identifiers known at scan time without
requiring the current placeholder location IDs to be valid database UUIDs.
Nullable location foreign keys should only be populated after real location
records exist.

If object upload fails, do not insert a row. If row insertion fails after upload,
delete that exact object path immediately as compensation. A scan that is not
fully persisted must not be returned by Recent Scans.

## Read contracts

Latest Demo scans (the client display limit is not a retention rule):

```sql
select id, created_at, stress_level, severity_score, confidence,
       diagnosis, location_snapshot, image_path
from scans
where data_stage = 'demo'
  and data_purpose = 'user_upload'
  and status = 'succeeded'
order by created_at desc
limit 10;
```

Detail reopening reads one row by ID with the same stage, purpose, and status
filters, returns `analysis_result`, and obtains the image through a short-lived
signed URL generated by the backend. Do not expose `raw_model_response` to app
clients.

## Safe Demo deletion

Deletion is a deliberate backend/admin operation, never a client-side cascade:

1. Select exact rows where `data_stage = 'demo'` and
   `data_purpose = 'user_upload'`, retaining the IDs and `image_path` values.
2. Delete those exact paths through the Supabase Storage API.
3. Call `delete_demo_user_upload_scan_records(ids)` for the matching IDs.
4. Compare requested object/row counts with deleted counts and report failures
   without logging images, secrets, or full analysis results.

Delete Storage objects through the Storage API rather than directly modifying
the `storage` schema. If row deletion fails after object deletion, retry the
database step; this is safer than deleting rows first and leaving untracked
private images.

## Data-purpose boundary

All current Demo uploads are product data with
`data_purpose = 'user_upload'`. They must never be copied, exported, queried, or
relabelled into a training or evaluation dataset. Any future expert-labelled
training images require a separate approved dataset, storage boundary, schema,
and ingestion workflow.

## Notes

- The schema uses `growing_tables` instead of `tables` because `tables` is easy to confuse with SQL/system naming.
- `growing_tables_create_rows` auto-creates row records when a table is inserted.
- `crops_one_active_per_row` prevents two active crops from being assigned to the same row.
- RLS is included for Supabase client access, but the recommended first implementation routes app traffic through FastAPI.
