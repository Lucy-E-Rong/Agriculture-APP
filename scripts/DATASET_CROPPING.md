# 本地原图裁切与质检

在项目根目录的 VS Code 终端运行，Python 3.10 或更高版本。

程序先寻找每株的高密度叶冠中心（近似菜心），再按相邻植株间距估算叶冠范围，
裁取约 120% 范围。邻株叶片可以进入裁片，不会因此剔除；目标是让裁片中央存在
一颗明确主体。对靠近原图边缘的候选，计算预计裁切范围留在原图内的面积比例，
低于 70% 才剔除。这里的 70% 是几何估算，不是准确的叶片实例分割比例。

实际抽测包括 Period 1 连续10张，以及5个Period各1张。前者保存70张、复核1张、
边缘剔除38张，耗时7.27秒；跨Period测试保存34张、边缘剔除23张，耗时3.58秒，
均无读取错误。预览抽查中主体整体明确，仍可见少量裁框偏大、包含较多邻株的情况。

2026-09-27全量处理263张原图，输出1956张JPEG裁片、4个复核候选、940个边缘
剔除候选，0个处理错误。裁片文件合计约598 MiB；产品负责人随后确认完成人工
视觉质检并接受该数量。当前仍无症状或水分胁迫专家标签。

```sh
python3 -m venv .venv-dataset
.venv-dataset/bin/python -m pip install -r scripts/dataset-requirements.txt
.venv-dataset/bin/python scripts/crop_dataset.py --limit 10
```

检查这 10 张的预览后，全量运行：

```sh

```

默认输入 `Photos/Photos`，递归读取 HEIC/HEIF/JPEG/PNG。全程本地，不调用
Gemini、数据库或网络服务。安装依赖需要联网。原图不会修改。

## 输出

每次运行建立独立 `dataset/run_日期_时间/`，不会覆盖上一次结果：

- `images/Period 1/IMG_8346_02.jpg`：通过规则的单株候选。编号为原图内候选
  从上到下、同排从左到右的顺序；被跳过的候选也占编号，所以可能不连续。
- `previews/`：原图缩略预览，绿框为保存候选，橙框需复核，红框为预计完整度
  低于阈值的剔除候选。
  框和编号只在预览上，裁片不含标记。
- `manifest.csv`：Excel 可打开的 UTF-8 BOM 清单；记录源文件、编号、像素坐标、
  处理结果、原因、清晰度、曝光及输出大小。坐标针对按 EXIF 方向校正后的原图，
  格式为左、上、右、下，右/下不包含。没有症状或水分胁迫标签。
- `summary.json`：参数、数量、耗时。没有检测到候选的原图也明确写入清单。

裁片保持宽高比，不放大，最长边 1600 像素。从 JPEG 质量 90 逐步降低以确保
每张严格小于 2,000,000 字节；必要时继续缩小。去掉 EXIF/GPS 等元数据。
这比 App 上传时的质量 70 保留更多细节；App 仍会执行自身的上传处理。

## 检测原理与边界

采用颜色分割（绿/黄绿与红紫）、形态学处理、叶冠密度峰值和相邻中心间距。
预计主体可见比例低于70%时跳过；菜心信号弱、模糊、曝光异常或短边不足
300像素时只登记复核，不输出裁片。邻株叠加和进入裁片是允许的。
模糊检查在最长边 512 像素的小图上计算，避免大图天然得到更高分数。

这是保守启发式筛选，不是经过训练的生菜实例识别模型。
绿色背景、棕色枯叶、严重萎蔫、重叠叶片可能导致漏检、重复中心或误检。
背景内部的遮挡、缺失叶片和真正的主体完整度无法由几何比例准确判断。
绿色框表示通过规则，不代表已经人工确认完整单株。
请查看预览；裁片数量以实际质检为准，不保证达到 2000。
本轮不自动猜测症状，不把过筛图片标记为“健康”。

进度条显示已处理数量、百分比、已用时间、预计剩余时间、速度和累计计数。
程序按单张处理，不把全部原图装入内存。Ctrl+C 停止后保留已完成产物；下次
重新运行会新建批次（尚无断点续跑），每张处理完立即刷新清单。

可选参数：`--input 路径`、`--output 路径`、`--limit N`、`--min-side 300`、
`--blur-threshold 35`、`--min-visible-fraction 0.70`。阈值应通过预览验证，
不建议为增加数量盲目降低。自动剔除会改变数据分布，需检查严重症状是否漏检。
